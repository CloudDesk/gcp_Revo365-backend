# PUC Null on Computer / Spares Products — Incident, Fix & Future Plan

_Last updated: 2026-10-20_

## 1. Incident summary

| Item | Detail |
|---|---|
| Environment | PROD |
| Product | `product_revo.id = 3460` — HP ProDesk 400 G4 Desktop Mini PC (category `refurbished`, subcategory `computer`) |
| Symptom | `puc` was `NULL` |
| Created / modified | `createddate = 1792370744`, `modifieddate = 1792400238` (~8 hours later → edited after creation) |
| Stock impact | None — no `stock_revo` rows for this product; no stock rows with null/orphan PUC in PROD |
| Data fix | `UPDATE product_revo SET puc = generate_puc('co', 're') WHERE id = 3460 AND puc IS NULL;` — applied successfully |

## 2. How PUC is generated

PUC is generated by the database, not application code.

- Trigger: `set_puc_trigger` — **`BEFORE INSERT`** on `product_revo` → `set_puc()`
- `set_puc()` (source: `src/database/migrations/20260728_product_computer_configuration.sql`)
  - Keeps `NEW.puc` if not null.
  - Category suffix from picklist `product_revo_category` → `metadata_json.pucSuffix` (new `nw`, used `ud`, refurbished `re`).
  - Subcategory prefix from picklist `product_revo_subcategory` → `metadata_json.pucPrefix` (laptop `la`, mobile_phone `mp`, accessories `ac`, computer `co`, spares `sp`).
  - Raises an exception if either is missing/inactive (so an INSERT can never silently produce a null PUC).
  - `NEW.puc := generate_puc(prefix, suffix)`.
- `generate_puc(cat, subcat)` → `cat || '-' || subcat || '-' || generate_alphanumeric_part(nextval('puc_seq_product_revo'))`
  e.g. `co-re-0000000296`.
- `stock_revo` has **no product id column** — stock is linked to a product **only via `puc`**.

PROD `set_puc()` was verified to match the repo version (picklist-driven, raises on bad category/subcategory). Category/subcategory picklists for product 3460 were active and correct (`re`, `co`).

## 3. Root cause

The trigger runs on INSERT only; the PUC was wiped by a later **UPDATE from the Inventory edit form**.

1. Edit save payload (`GCP-Latest-Revo-Inventory/src/Pages/V1|V2/ProductPage/DetailPage/ProductForm.tsx`):
   ```ts
   let allFileds = { ...formValues.otherFields, ...categories, ...values };
   ```
2. `otherFields` = `allInialValuesSpread` in `getProductInitialValues.tsx` — the merged **defaults of every product form**, which include `puc: null`, `quantity: 0`, `availablequantity: 0`, `discount: 0`, `isfeaturedproduct: false`, etc.
3. Laptop / mobile / accessory `*SavedValues(record)` copy those fields from the loaded product, so they override the defaults.
4. `ComputerSavedValues` / `SpareSavedValues` (added with the July computer-configuration change) did **not** include them, so the defaults were sent.
5. Backend `upsertProductrevo` (`src/services/productrevo.service.ts`) builds `UPDATE product_revo SET <every payload key> …` with no filtering (request schema validation on `/v2/product` is commented out in `src/routes/routes.ts`).

### Fields that were being reset on every Computer / Spares edit

| Field(s) | Reset to |
|---|---|
| `puc` | `NULL` |
| `quantity`, `availablequantity`, `soldquantity`, `ecompublishedquantity` | `0` |
| `rentaltotalquantity`, `rentalavailablequantity`, `rentalsoldquantity` | `0` |
| `discount` | `0` |
| `isfeaturedproduct` | `false` |
| `productstatus`, `ponumber`, `productcondition`, `brandlabel`, `colour`, `weight`, `dimensions` | `NULL` |

Remaining default-only keys (~100) are spec fields of other product types (camera, IMEI, headset, …) — always null for computers/spares; laptops/mobiles send them the same way today.

## 4. Fix shipped (Phase 1 — Frontend)

- Repo: `GCP-Latest-Revo-Inventory`, branch `PROD`, commit `9cf4cdd`
- File: `src/Schema/FormsInitialValues/ComputerAndSpares.tsx`
- Added `preservedProductValues(record)` and spread it into `ComputerSavedValues` and `SpareSavedValues`. It carries the stored `puc`, quantity counters, `discount`, `productstatus`, `isfeaturedproduct`, `ponumber`, `productcondition`, `brandlabel`, `colour`, `weight`, `dimensions` — same pattern as `NewLaptopSavedValues` etc.
- `quantityforlocation` falls back to `null` (not `0`) so a null JSONB column is written back unchanged.
- Covers both V1 and V2 product forms (both use these SavedValues).

**Verification done**
- Ran `getProductInitialValues` for computer/spares with a sample product (quantity 5, available 3, discount 10, featured, PUC set): payload now carries the stored values; no important field falls back to a default.
- `tsc --noEmit`: 0 errors.

## 5. Known remaining risk (all product types)

Quantity counters sent by the edit form are a **snapshot taken when the edit page was opened**. If stock changes (order, stock-in, rental) while the page is open, saving writes the old numbers back. No recalculation runs after `/v2/product` saves. This affects laptops, mobiles and accessories today, and now Computer/Spares too (previously they were reset to 0, which was worse).

## 6. Future plan

### Phase 2 — Backend PUC guard (ready, not deployed)

- Repo: `gcp_Revo365-backend`, file `src/services/productrevo.service.ts`, function `upsertProductrevo` (local change, uncommitted).
- Drops `puc` from the payload when it is `null`/`undefined`/blank:
  - UPDATE → existing PUC is never cleared, regardless of client.
  - INSERT → `set_puc_trigger` always generates the PUC (a `''` value previously bypassed the trigger).
- All `/v2/product` callers checked (product forms, list actions, archive, recycle bin, title edit) — none needs to clear a PUC.
- Deploy with the next backend release; test on UAT first.

### Phase 3 — Backend: ignore system-managed stock counters on UPDATE (proposed)

- In `upsertProductrevo`, on UPDATE only, remove: `quantity`, `availablequantity`, `soldquantity`, `ecompublishedquantity`, `oncatalogueqty`, `offcatalogueqty`, `quantityforlocation`, `orderedquantity`, `rentaltotalquantity`, `rentalavailablequantity`, `rentalsoldquantity`, `reservedforrentalquantity`, `serviceholdquantity`, `damagedquantity`, `lostquantity`, `lock_qty`, `bin_qty`, `archive_qty`, `ewaste_qty`.
- Keep `discount`, `productstatus` (user-editable). INSERT unchanged.
- These counters are owned by the stock flows (`stockRevoService.updateQuantity`, `productrevoService.updateCatalogueQuantities`).
- Before implementing: confirm no screen intentionally sets quantities through `/v2/product`; list callers and grep for quantity writes.
- Removes the stale-overwrite risk (section 5) for every product type.

### Phase 4 — Hardening (optional)

- Make `puc` immutable at DB level: `BEFORE UPDATE` trigger that keeps `OLD.puc` when `NEW.puc` is null/blank (defence for scripts, imports, other services).
- Stop sending `otherFields` (merged defaults of all forms) on edit, or restrict the payload to fields of the current form — removes the whole class of cross-form default leakage.
- Re-enable request schema validation on `POST /v2/product` with an allow-list of updatable columns.
- Monitoring query (scheduled / dashboard):
  ```sql
  SELECT count(*) FROM product_revo WHERE puc IS NULL OR BTRIM(puc) = '';
  ```

## 7. Runbook — if a product's PUC is null again

1. Inspect:
   ```sql
   SELECT id, puc, productname, category, subcategory, createddate, modifieddate FROM product_revo WHERE id = <id>;
   ```
2. Check for linked stock (stock links by PUC only):
   ```sql
   SELECT id, puc, productname, serialnumber FROM stock_revo WHERE puc IS NULL OR BTRIM(puc) = '';
   SELECT s.id, s.puc FROM stock_revo s LEFT JOIN product_revo p ON p.puc = BTRIM(s.puc)
   WHERE s.puc IS NOT NULL AND BTRIM(s.puc) <> '' AND p.id IS NULL;
   ```
3. If the product previously had a PUC that stock still uses → restore that exact value. Do **not** generate a new one.
4. Otherwise generate (prefix = subcategory, suffix = category):
   ```sql
   BEGIN;
   UPDATE product_revo SET puc = generate_puc('<prefix>', '<suffix>') WHERE id = <id> AND puc IS NULL RETURNING id, puc;
   COMMIT; -- or ROLLBACK if the result is wrong
   ```
   Prefixes: laptop `la`, mobile_phone `mp`, accessories `ac`, computer `co`, spares `sp`. Suffixes: new `nw`, used `ud`, refurbished `re`.
5. If stock rows need relinking, update `stock_revo.puc` to the product's PUC and trigger a quantity recalculation (re-save a stock row, which calls `updateQuantity` / `updateCatalogueQuantities`).

## 8. Data check for past damage

Computer/Spares products edited before the fix may have had quantities reset:

```sql
SELECT p.id, p.puc, p.subcategory, p.quantity, p.availablequantity, p.discount,
       (SELECT count(*) FROM stock_revo s WHERE s.puc = p.puc AND NOT COALESCE(s.isdeleted, false)) AS stock_rows
FROM product_revo p
WHERE LOWER(p.subcategory) IN ('computer', 'spares')
ORDER BY p.id;
```

Rows with `stock_rows > 0` but zero quantities were likely reset — recalculate via the stock flows.
